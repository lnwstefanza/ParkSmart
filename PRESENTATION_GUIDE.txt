ตอนที่ 1: สคริปต์พูดเปิดตัวและภาพรวมระบบ (แนะนำตัวใน 2 นาที)
--------------------------------------------------------------------------------
"กราบเรียนอาจารย์ที่เคารพ กระผมนายคณาทิพย์ ขอแนะนำโปรเจกต์ 'ParkSmart' ครับ

[ปัญหาที่พบ (Problem Statement)]
ในตัวเมืองขอนแก่น เช่น บริเวณเซ็นทรัลขอนแก่น ตลาดต้นตาล หรือแฟรี่พลาซ่า มักเกิดปัญหาการจราจรติดขัดจากการที่รถต้องขับวนหาที่จอด ทำให้เสียเวลา เปลืองน้ำมัน และไม่สามารถคาดการณ์ได้ว่าจะมีที่จอดว่างหรือไม่

[วิธีแก้ปัญหา (Our Solution)]
พวกเราจึงพัฒนาระบบ 'ParkSmart' ซึ่งเป็นระบบบริหารและจองที่จอดรถออนไลน์อัจฉริยะ ช่วยให้:
1. ลูกค้า (Customer) สามารถค้นหาลานจอด เช็คสถานะช่องจอดแบบเรียลไทม์ และจองช่องจอดล่วงหน้าพร้อมชำระเงินมัดจำผ่านระบบ QR Code ได้
2. เจ้าของลานจอด (Parking Owner) สามารถจัดการช่องจอด ตรวจสอบการเข้า-ออกของรถ และดูสถิติรายได้แบบโปร่งใส
3. ผู้ดูแลระบบ (Administrator) สามารถตรวจสอบโครงสร้างฐานข้อมูล (Database Inspector) จัดการข้อร้องเรียน และดูรายงานภาพรวมได้

โดยระบบนี้ถูกออกแบบโครงสร้างฐานข้อมูลเชิงสัมพันธ์ (Relational Database) ตามหลักการ Normalization (3NF) ครบถ้วนตาม Relational Diagram 11 Entities ครับ"

--------------------------------------------------------------------------------
ตอนที่ 2: อธิบายสถาปัตยกรรมระบบ (System Architecture & Tech Stack)
--------------------------------------------------------------------------------
สถาปัตยกรรมของ ParkSmart แบ่งออกเป็น 3 เลเยอร์หลัก:

1. Frontend (ฝั่งผู้ใช้งาน):
   - พัฒนาด้วย React 19 + TypeScript + Vite
   - ตกแต่งด้วย Tailwind CSS และชุดไอคอน Lucide-React
   - รองรับ Responsive ใช้งานได้ทั้งบนสมาร์ทโฟนและคอมพิวเตอร์
   - Deploy ขึ้นระบบคลาวด์บน Firebase Hosting (https://parksmart-fb86b.web.app)

2. Backend (ฝั่งเซิร์ฟเวอร์และ API):
   - พัฒนาด้วย Node.js + Express REST API
   - ยืนยันตัวตนด้วย JSON Web Token (JWT) และความปลอดภัยรหัสผ่านด้วย bcryptjs
   - มีระบบสร้าง QR Code สำหรับบัตรจอดรถอัตโนมัติ

3. Database Engine & Cloud Integration (Firebase Cloud Firestore):
   - Cloud Database: ย้ายและซิงค์ข้อมูลทุก Entity ขึ้น Firebase Cloud Firestore (parksmart-fb86b) แบบเรียลไทม์
   - รองรับการทำงานได้ 100% บน Firebase Hosting แบบ Serverless โดยมี Firebase Client Adapter (client/src/lib/firebase-adapter.ts)
   - Dual-Engine & Backup: รองรับ SQLite Engine (server/parking.db) บนเครื่อง Local พร้อมระบบ Auto-Sync สองทิศทาง และสอดคล้องกับมาตรฐาน Oracle SQL DDL

ตอนที่ 3: หัวใจสำคัญของฐานข้อมูล (Database Schema & Relational Design)
--------------------------------------------------------------------------------
*เน้นจุดนี้เป็นพิเศษเวลาพรีเซนต์วิชา Database*

โครงสร้างตารางหลักทั้ง 11 Entities (ตรงตาม Relational Diagram):

1. Customer: จัดเก็บข้อมูลลูกค้า (Customer_ID [PK], Username [UNIQUE], Password_Hash, Phone_Number, Email)
2. Parking_Owner: บัญชีเจ้าของลานจอดรถ (ParkingOwner_ID [PK], Bank_Account สำหรับรับโอนเงิน)
3. Administrator: ผู้ดูแลระบบ (Admin_ID [PK], Username, Email)
4. ParkingLot: ข้อมูลลานจอดรถ (Lot_ID [PK], ParkingOwner_ID [FK], พิกัด Lat/Long, FeeRate, เวลาเปิด-ปิด)
   - Constraint: UQ_Lot_Location ป้องกันการสร้างชื่อลานจอดและสถานที่ซ้ำซ้อน
5. ParkingSlot: ข้อมูลช่องจอดรายช่อง (Slot_ID [PK], Lot_ID [FK], SpaceCode เช่น A01, Floor, Zone, Status)
   - Constraint: มี Foreign Key ชี้ไป ParkingLot พร้อม ON DELETE CASCADE และ Unique (Lot_ID, SpaceCode)
6. FavoriteLot: ลานจอดที่ผู้ใช้บันทึกเป็นรายการโปรด (Weak Entity / M:N Association)
   - Composite Primary Key: (Customer_ID, Lot_ID) ป้องกันการบันทึกรายการซ้ำ
7. Reservation: ธุรกรรมหัวเอกสารการจอง (Booking_ID [PK], Customer_ID [FK], ReserveDate)
8. Reservation_Detail: รายละเอียดรายการจอง (Detail_ID หรือ Composite PK [Booking_ID, Slot_ID])
   - เก็บข้อมูล LicensePlate (ทะเบียนรถ), StartTime, EndTime, Totalfee, Reservation_Status, และ QRToken [UNIQUE]
9. UsageLog: บันทึกประวัติการนำรถเข้า-ออกจริง (Log_ID [PK], Booking_ID [FK], Slot_ID [FK], Actual_Check_In, Actual_Check_Out)
   - ใช้สำหรับคำนวณค่าจอดเกินเวลาจริง (Overtime Fee) และคืนเงินมัดจำ
10. Payment: ประวัติธุรกรรมการเงิน (Payment_ID [PK], Booking_ID [FK], Amount, Payment_Type, Payment_Status)
11. Complaint: ข้อร้องเรียนจากผู้ใช้ (Complaint_ID [PK], Booking_ID [FK], Customer_ID [FK], Admin_ID [FK])

* ตารางเสริม: AuditLog - บันทึกประวัติการทำงานของระบบ (Who, When, What action) เพื่อความถูกต้องของข้อมูลตามหลัก Database Auditing

ตอนที่ 4: เจาะลึก Source Code รายไฟล์ (Code Walkthrough)
--------------------------------------------------------------------------------
เวลาอาจารย์ให้เปิดโค้ด ให้พาอาจารย์ดูตามลำดับนี้:

[ส่วนที่ 1: ฝั่ง Database & Schema Scripts]
1. parksmart_schema.sql / parksmart_oracle_full.sql:
   - อธิบายอาจารย์ว่า: "ไฟล์นี้คือคำสั่ง Oracle SQL DDL มาตรฐาน มีการสร้างตารางครบ 11 ตาราง มี Primary Key, Composite Key, Foreign Key Constraints, และ Check Constraints ครบถ้วนตามแบบจำลองความสัมพันธ์ (Relational Model)"
2. server/schema-ddl.js:
   - บรรจุ Schema DDL เดียวกันไว้ในฝั่ง Backend เพื่อใช้ตรวจสอบและแสดงผลในระบบ Admin
3. server/db.js:
   - ฟังก์ชัน initDatabase(): สร้าง Table ทั้งหมดใน SQLite พร้อมสร้าง Triggers ตรวจสอบและอัปเดตข้อมูลอัตโนมัติ
   - ฟังก์ชัน seedData(): มีข้อมูลจำลองพร้อมใช้งาน ทั้งลานจอดจริงในขอนแก่น (เซ็นทรัล, ตลาดต้นตาล, แฟรี่ ฯลฯ) ช่องจอด และบัญชีผู้ใช้ทดสอบ 3 กลุ่ม

[ส่วนที่ 2: ฝั่ง Backend API (server/index.js)]
1. Authentication & Security (บรรทัด ~35-60):
   - ฟังก์ชัน authenticate() และ requireRole(): ใช้ JWT Token ตรวจสอบสิทธิ์ (RBAC: Role-Based Access Control) แบ่งเป็น Customer, Owner, Admin
2. Booking Transaction Logic (ส่วน /api/reservations):
   - ฟังก์ชันตรวจสอบ Availability ป้องกัน Double Booking (การจองช่องเดียวกันในช่วงเวลาทับซ้อนกัน)
   - การสร้าง QR Code ด้วยไลบรารี qrcode แล้วแปลงเป็น Data URL ส่งให้ลูกค้า
3. Check-In / Check-Out Calculation Engine (ส่วน /api/scan/check-in และ /check-out):
   - เมื่อสแกน Check-in: บันทึก Actual_Check_In ใน UsageLog และปรับสถานะ ParkingSlot เป็น 'Occupied'
   - เมื่อสแกน Check-out: ดึงเวลา Actual_Check_Out มาเปรียบเทียบกับ EndTime ที่จองไว้
     -> หากเกินเวลา: คำนวณ Overtime Penalty ตามจำนวนชั่วโมงจริง
     -> บันทึกรายการ Payment และปรับสถานะช่องจอดกลับเป็น 'Available'

[ส่วนที่ 3: ฝั่ง Frontend (client/src/)]
1. client/src/App.tsx:
   - กำหนด Route ของระบบทั้งหมด แยกหน้าตามสิทธิ์ของผู้ใช้
2. client/src/pages/Booking.tsx & Payment.tsx:
   - หน้าฟอร์มการเลือกช่องจอด วันที่ เวลา คำนวณราคาแบบ Interactive พร้อมหน้าจำลองการชำระเงินมัดจำ
3. client/src/pages/TicketDetail.tsx:
   - หน้าแสดงบัตรจอดรถดิจิทัล มี QR Code แบบไดนามิก พร้อมปุ่มจำลองการสแกน Check-in / Check-out เสมือนจริง
4. client/src/pages/admin/AdminDatabaseInspector.tsx:
   - ไฮไลต์สำหรับวิชา Database: มีหน้า SQL Query Runner ที่อาจารย์สามารถพิมพ์คำสั่ง SELECT SQL ดูข้อมูลใน Database ได้แบบสดๆ และมี Diagram Viewer อธิบายความสัมพันธ์

ตอนที่ 5: ลำดับขั้นตอนการสาธิตระบบ (Live Demo Step-by-Step)
--------------------------------------------------------------------------------
ขั้นตอนที่ 1: เปิดหน้าเว็บหลัก (Home / Lots)
- เปิดเว็บ https://parksmart-fb86b.web.app หรือ http://localhost:3000
- ชี้ให้อาจารย์ดูลานจอดรถในขอนแก่น เช่น ลานเซ็นทรัล ขอนแก่น
- แสดงการค้นหา การกรองตามอำเภอ และสถานะช่องจอดว่างแบบเรียลไทม์

ขั้นตอนที่ 2: จำลองการจอง (Customer Flow)
- เข้าสู่ระบบด้วยบัญชี Customer (Username: customer1 / Password: cust123)
- เลือกลานจอด -> เลือกรอบเวลาและเลือกช่องจอด เช่น ช่อง A01
- กด "ดำเนินการจอง" -> ไปที่หน้าชำระเงินมัดจำ
- ชำระเงินเสร็จสิ้น -> ระบบออกบัตรจอดรถพร้อม QR Code ทันที

ขั้นตอนที่ 3: จำลองการเข้า-ออกลานจอด (Parking Flow)
- เปิดหน้าตั๋วการจอง (Ticket Detail)
- กดปุ่ม "จำลองการสแกนเข้า (Check-In)"
  -> อธิบายว่า: "ระบบจะบันทึก Actual_Check_In ใน UsageLog และเปลี่ยนสถานะช่องเป็น Occupied"
- กดปุ่ม "จำลองการสแกนออก (Check-Out)"
  -> อธิบายว่า: "ระบบจะคำนวณระยะเวลาจริง หักเงินมัดจำ คำนวณค่าบริการสุทธิ และบันทึก Payment พร้อมคืนสถานะช่องจอดเป็น Available"

ขั้นตอนที่ 4: แสดงหน้า Admin Database Inspector (สร้างความประทับใจให้อาจารย์)
- เข้าสู่ระบบด้วยบัญชี Admin (Username: admin / Password: admin123)
- ไปที่เมนู "ตรวจสอบฐานข้อมูล (Database Inspector)"
- รัน SQL Query ตัวอย่าง เช่น:
  SELECT * FROM Reservation_Detail WHERE Reservation_Status = 'Completed';
- แสดงให้อาจารย์เห็นว่าข้อมูลถูกบันทึกตาม Schema และ Referential Integrity ถูกต้อง 100%

ตอนที่ 6: รวมคำถามยอดฮิตที่อาจารย์มักจะถาม (Q&A) พร้อมแนวทางการตอบ
--------------------------------------------------------------------------------

คำถามที่ 1: "ทำไมต้องแยกตาราง Reservation กับ Reservation_Detail ออกจากกัน?"
แนวคำตอบ:
"เนื่องจากเป็นไปตามหลักการ Normalization (3NF) ครับ ในหนึ่งการจอง (Reservation Header) จะมีข้อมูลระดับธุรกรรม เช่น วันที่จอง และรหัสลูกค้า ส่วน Reservation Detail จะเก็บข้อมูลระดับรายการ เช่น ทะเบียนรถ ช่องจอด ช่วงเวลาเริ่มต้น-สิ้นสุด และ QR Code ซึ่งทำให้ในอนาคตระบบสามารถขยายรองรับการจองครั้งละหลายช่องจอดในหนึ่งบิลได้ครับ"

คำถามที่ 2: "ระบบป้องกันการจองชนกัน (Double Booking) ในช่องจอดเดียวกันอย่างไร?"
แนวคำตอบ:
"ก่อนที่ระบบจะสร้าง Reservation_Detail Backend จะมีฟังก์ชันตรวจสอบเงื่อนไขช่วงเวลา (Time Overlap Query) โดยตรวจสอบว่า ในช่องจอดเดียวกัน มีรายการจองอื่นที่สถานะเป็น Confirmed หรือ Checked_In ที่มีช่วงเวลา Expected_Arrival ถึง Booked_End ซ้อนทับกับเวลาที่ลูกค้าต้องการจองหรือไม่ หากมี ระบบจะปฏิเสธการจองทันทีครับ"

คำถามที่ 3: "ทำไมถึงมีทั้งไฟล์ Oracle SQL DDL และ SQLite Database?"
แนวคำตอบ:
"ไฟล์ parksmart_oracle_full.sql ถูกเขียนขึ้นตามข้อกำหนดมาตรฐานของ Oracle PL/SQL เพื่อแสดงความถูกต้องของ Data Dictionary, Data Types (VARCHAR2, TIMESTAMP, NUMBER), Constraints และ ER Diagram ของวิชาฐานข้อมูล ส่วน SQLite ถูกนำมาใช้เป็น Database Engine ตัวจริงในการรันเว็บแอปพลิเคชัน เพื่อให้ระบบมีความรวดเร็ว น้ำหนักเบา และสามารถพกพาไปสาธิตได้ทุกที่โดยไม่ต้องติดตั้ง Oracle Instance ขนาดใหญ่ครับ"

คำถามที่ 4: "ระบบนี้มีการนำความปลอดภัยของข้อมูลมาใช้อย่างไรบ้าง?"
แนวคำตอบ:
"1. รหัสผ่านของผู้ใช้ทุกคนถูกเข้ารหัสด้วยอัลกอริทึม bcrypt พร้อม salt ก่อนบันทึกลงฐานข้อมูล จึงไม่มี Plaintext Password หลุดรอด
 2. ใช้ JWT Token ในการตรวจสอบสิทธิ์ของผู้ใช้งานในระดับ API (Role-Based Access Control)
 3. ฝั่ง Database Console อนุญาตเฉพาะคำสั่งอ่านข้อมูล (SELECT) เพื่อป้องกัน SQL Injection หรือการสั่ง DROP/DELETE โดยไม่ได้รับอนุญาตครับ"
